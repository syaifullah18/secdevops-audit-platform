# WS3 Normalizer + findings store

- **Runner / model:** claude / `claude-sonnet-5-5` (fallback agy / `gemini-4-argon-high`)
- **Branch:** `ws/WS3`
- **Paths:** `packages/normalizer/**`, `apps/api/src/db/**` (plus `apps/api/drizzle/**` for migrations
  and the `drizzle-orm`/`pg`/`drizzle-kit` dependency lines in `apps/api/package.json`)
- **Consumes (core):** `Finding`, `TraceStep`, `EvidenceItem`, `Fingerprint`, `Verdict`, `Severity`,
  `FindingStatus`, `computeSlaDue`, `SlaDays`, `Store` and all repo interfaces, `AccessScope`

## Goal

Turn the skill's outputs into tracked, deduplicated findings, and persist everything in
PostgreSQL with Drizzle.

## Deliverables

### packages/normalizer

1. Zod schemas for the skill's raw `findings.json` (all three verdict variants, mirroring
   `vendor/security-audit-skill/skills/security-audit/report-schema.json`) and for
   `coverage-ledger.json` units (fields listed in `validate-coverage-ledger.cjs`).
2. **Verdict mapping**: canonical words plus legacy/model words:
   `CONFIRMED|VALID|TRUE_POSITIVE → confirmed`, `PLAUSIBLE|PARTIAL|NEEDS_VALIDATION|UNVERIFIED|
INCONCLUSIVE → needs_validation`, `REFUTED|REJECTED|FALSE_POSITIVE|INVALID → rejected`
   (case/space/hyphen-insensitive). Unknown words → error, never a silent default.
3. **Salvage**: a tolerant reader that recovers an array from concatenated JSON objects and strips
   provider filter notices around JSON; returns `{ value, salvaged: boolean, warnings }`. The
   worker still runs the skill validator afterwards.
4. `normalizeRun({ findings, ledger, run, project, model, now, slaDays })` → `Finding[]`:
   location = sink trace step else first step; `attackClass` from the ledger unit whose
   `result_fingerprints` contains the fingerprint (`canonical_refs.attack_class` mapped to a
   family where possible), else `other` (see `docs/decisions.md` D-006); `originalSeverity` from
   the hunter candidate if provided, `verifiedSeverity` = `severity.overall_severity` for
   confirmed; blockers from `blockers`; rejection reason from `reason`.
5. **Fingerprinting**: keep the skill's `fingerprint` as primary identity. Provide
   `secondaryFingerprint(finding)` (hash of attack class + normalized sink file + scope + root
   cause words, line-number independent) for carry-forward when code moves.
6. **Merge/dedup** `mergeFindings(existing, incoming, now)`: match by fingerprint, then secondary
   fingerprint; carry `status`, `owner`, `firstSeen`, `firstRun`; update `lastSeen`, `sourceRun`;
   verdict change rules: `confirmed → rejected` in a later run keeps status but records it;
   `fixed` + seen again → back to `confirmed` (regression). Repeat-N merge: same fingerprint
   from multiple runs → one finding, confidence raised.
7. SLA via `computeSlaDue` on verified severity from `firstSeen`.

### apps/api/src/db

8. Drizzle schema for projects, runs, run_phases, slices (attempts as jsonb), findings
   (unique `(project_id, fingerprint)`, index on secondary fingerprint), triage_events,
   policies, exceptions, events (append-only, unique `(run_id, seq)`), decisions.
9. Migrations under `apps/api/drizzle/` generated by drizzle-kit.
10. `createPgStore(databaseUrl): Store` implementing every repo interface in
    `packages/core/src/store.ts`, enforcing `AccessScope` on every finding/project/run read via a
    join on `projects.client_id`. `upsert` uses `mergeFindings` semantics.

## Acceptance criteria

- **Golden-file tests**: `packages/normalizer/test/golden/` with synthetic skill outputs
  (confirmed, needs_validation, rejected, legacy verdict words, concatenated JSON) and expected
  normalized `Finding[]` JSON. All synthetic: sample-app paths only, no real code.
- Every normalized finding passes `Finding.parse`.
- Dedup test: same finding in run 2 at a moved line → same id, `firstSeen` kept, status carried.
- Store tests run against PostgreSQL when `DATABASE_URL` is set (skip otherwise, with a clear
  skip message); include an isolation test (scope excludes another client's findings).
- `pnpm -r typecheck lint test` green. READMEs for the normalizer and the db module.

## Out of scope

HTTP routes (WS2), calling the normalizer from the worker (Phase 2 wiring).
